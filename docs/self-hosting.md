# Security and self-hosting

Agentman uses TLS between each client and the relay, but it does not provide
end-to-end payload encryption or authentication between the daemon and mobile
app. A relay operator can inspect, alter, or inject live traffic, including
agent-control requests.

Use the public relay only when that trust boundary is acceptable. Otherwise,
deploy the relay yourself and point both `am serve` and `am pair` at it.

## Security model

- Pairing and WebSocket control endpoints require bearer credentials or a
  single-use pairing secret. `GET /health` is public and reports aggregate
  connection counts and relay version information.
- Typed pairing codes are ten digits, rate-limited, single-use, and valid for
  60 seconds. QR pairing uses an independent high-entropy token.
- Device credentials are signed, expire after one year, and are not stored in a
  device database. They cannot be revoked individually before expiry.
- The relay has no persistent transcript, message, notification, or account
  database. It does keep volatile connection and pairing state in memory.
- Live transcript content traverses the relay when requested. "Transcripts stay
  on your computer" means the source files and durable history remain local,
  not that transcript content never leaves the computer.
- Native app credentials use Expo SecureStore. Web builds use browser-backed
  storage.
- Local hook requests are token-authenticated and accepted only on numeric
  loopback addresses.
- Wire protocol v2 rejects incompatible clients before routing their requests.

The app sends its Expo push token to the daemon through the relay during
registration, so the relay can observe that token. Notification delivery then
follows a separate path from the daemon to Expo and the platform push provider;
the notification payload does not pass through the relay, but those third
parties can process it.

When speech is enabled, Agentman sends prepared agent output and a bearer token
to the configured speech endpoint. Use HTTPS for remote speech endpoints and
treat that service as another content and credential trust boundary.

## Relay requirements

The relay binary serves plain HTTP. Production deployments must put it behind a
TLS-terminating reverse proxy or platform load balancer because Agentman rejects
remote plaintext relay URLs.

The relay requires a stable `AGENTMAN_RELAY_SECRET` of at least 16 characters.
Do not generate a new secret on every container start. Rotating it invalidates
all existing device credentials and requires every phone to pair again.

## Docker behind TLS

Create a private environment file outside the repository and generate its
stable secret once:

```bash
umask 077
install -d -m 700 "$HOME/.config/agentman"
printf 'AGENTMAN_RELAY_SECRET=' > "$HOME/.config/agentman/relay.env"
openssl rand -hex 32 >> "$HOME/.config/agentman/relay.env"
printf 'PORT=8080\nAGENTMAN_TRUST_PROXY=1\n' >> "$HOME/.config/agentman/relay.env"
```

Build and bind the relay only to host loopback:

```bash
docker build -t agentman-relay .
docker run --name agentman-relay \
  --env-file "$HOME/.config/agentman/relay.env" \
  -p 127.0.0.1:8080:8080 \
  agentman-relay
```

Then terminate TLS in a reverse proxy. For example, a host-level Caddy
configuration can proxy a public hostname to the loopback container:

```caddyfile
relay.example.com {
  reverse_proxy 127.0.0.1:8080
}
```

The example enables `AGENTMAN_TRUST_PROXY` because Caddy overwrites
`X-Forwarded-For`. Enable it only behind a proxy with that behavior. It lets
per-client pairing and connection limits use the original client address rather
than the proxy address.

Point Agentman at the HTTPS hostname:

```bash
am serve -relay https://relay.example.com
am pair -relay https://relay.example.com
```

You can persist the selection with `AGENTMAN_RELAY`.

## Railway

The included [`railway.json`](../railway.json) builds the relay Dockerfile and
checks `GET /health` during deployment.

Deploy the repository to create and link its service:

```bash
railway up
railway variable set AGENTMAN_TRUST_PROXY=1
railway domain
```

In the service's Railway **Variables** page, set `AGENTMAN_RELAY_SECRET` to a
stable value generated by a password manager or a cryptographically secure
random generator. Using the dashboard avoids placing the secret in shell
history. Railway redeploys the service after variable changes. Keep the secret
in Railway rather than generating it in application startup commands.

Railway terminates TLS for its generated domain. `AGENTMAN_TRUST_PROXY=1` is
appropriate there because the application is behind Railway's proxy. Do not
enable it for a directly exposed relay where clients can supply forwarding
headers themselves.

## Health checks

`GET /health` is intentionally public. It returns JSON containing relay status,
version, active daemon/app counts, pending pairing count, and storage mode. A
healthy response confirms that the process is serving HTTP; it does not verify
that a specific daemon or phone is connected.

## Operational notes

- Relay state is in memory. Restarts disconnect clients and discard pending pairing codes.
- There is no offline frame buffer. Clients reconnect and request current state from the daemon.
- Preserve the relay secret across deploys and backups.
- Use WebSocket-compatible proxy timeouts for long-lived connections.
- Upgrade the daemon, app, and relay together when the wire protocol version changes.
